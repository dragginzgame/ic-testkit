# Shared-Incremental Cargo Wasm Caching

## Status

Implemented in `0.6.0` after the released `0.5.2` transactional-cache
maintenance. The `0.6.1` follow-ups add integration and observation APIs
without changing this ownership model. This design is additive: the existing
isolated, content-addressed Cargo target mode remains the default and retains
its cache format and behavior.

## Problem

`WasmBuildSpec` resolves Cargo's local dependency closure, configuration,
toolchain, arguments, environment, and additional inputs exactly. It currently
builds every fingerprint in an independent Cargo target directory. This makes
an exact old fingerprint reusable, but a source edit starts from a cold Cargo
target.

Consumers can instead combine `ArtifactCacheSpec` with a shared Cargo target,
but then they must reproduce Cargo input discovery and before/after
verification themselves. That duplicates correctness-sensitive code and makes
cache precision depend on every downstream adapter.

The library needs an opt-in mode that combines:

- the existing exact Cargo input model;
- Cargo's shared incremental compilation state;
- immutable, content-addressed final Wasm artifacts;
- cross-process coordination and input-race rejection;
- bounded retention that never owns the shared Cargo target.

## Public model

`WasmBuildSpec` gains an explicit shared-incremental target option. Without
that option, the existing isolated mode is unchanged. The caller-facing target
directory continues to own exact entries, stamps, locks, retention, and
materialized Wasm outputs. The shared Cargo target is separate mutable build
state owned by the caller.

Cargo argument, environment, inherited-environment, and additional-input
builders accept both string and OS-native iterator values through one generic
method per field.

Exact Cargo input resolution is also exposed as an opaque public snapshot. It
reports the complete fingerprint, source/configuration digest, resolved input
paths, exclusions, and phase timings without exposing internal metadata JSON.
The snapshot can be resolved again and compared after an external build. Raw
absolute checkout and destination paths do not become cache identity.

## Identity and ownership

The exact fingerprint continues to cover:

- selected Cargo packages;
- compilation target and profile-output identity;
- ordered Cargo arguments;
- effective relevant environment, including set and unset values;
- Cargo and rustc identities;
- workspace manifest, lockfile, toolchain files, effective Cargo
  configuration and recursive includes;
- every local package in the selected dependency closure;
- caller-declared additional inputs.

Build mode and target-directory locations are execution policy, not artifact
identity. An isolated and shared-incremental build with the same exact inputs
may reuse the same immutable Wasm entry. The shared target is excluded only as
known generated Cargo state; callers do not receive a general unsafe source
exclusion mechanism.

The caller-facing cache owns:

- fingerprint-named immutable entries;
- artifact content stamps and materialized outputs;
- cache, entry-use, and retention metadata;
- process-lock files.

The caller owns the shared Cargo target. `ic-testkit` may create it, tag it as
a cache, and coordinate its use, but never prunes or removes it after a failed
build.

## Locking and lifecycle

An acquisition first takes the existing caller-facing cache lock, resolves the
exact fingerprint, and checks materialized and immutable cached artifacts. An
exact hit never runs Cargo or touches the shared incremental target.

On a shared-incremental miss:

1. Remove only an incomplete immutable entry for the selected fingerprint.
2. Acquire a process lock derived from the canonical shared Cargo target.
3. Run Cargo with `CARGO_TARGET_DIR` set to that shared target.
4. Validate every expected nonempty Wasm output.
5. Resolve the exact Cargo inputs again.
6. Reject publication when the fingerprint changed during the build.
7. Stream the final Wasm files into the fingerprint entry.
8. Publish their exact content stamps.
9. Materialize caller-facing outputs atomically.
10. Record use and apply optional retention while protecting the active entry.

The cache lock deliberately gives the first implementation conservative
serialization. The shared-target lock additionally protects callers using the
same mutable Cargo target with different cache roots. A later optimization may
allow unrelated exact hits concurrently without changing the contract.

## Failure semantics

Failed Cargo execution, missing outputs, changed inputs, copy failures, and
panics never publish a reusable fingerprint entry. Cleanup removes only the
incomplete immutable entry. Shared Cargo incremental state is retained because
Cargo may have written valid reusable intermediates before failing.

If both the build and immutable-entry cleanup fail, the existing structured
combined error preserves both causes. The existing isolated mode continues to
remove its incomplete fingerprint-specific Cargo target on failure.

## Retention

Age and logical-size retention applies only to immutable fingerprint entries.
In shared mode those entries contain final Wasm artifacts and stamps rather
than complete Cargo target trees, so their retained size is bounded by output
sets. The active fingerprint remains protected. The shared Cargo target is
outside retention scope and remains caller-maintained.

No bounded policy becomes automatic. Documentation provides explicit starting
points and reminds callers that suitable limits depend on artifact count,
local disk, and CI cache policy.

## 0.6.1 integration follow-ups

Transactional external builds can attach a labeled `WasmBuildSpec` and its
`ResolvedCargoBuildInputs`. The resolved fingerprint contributes the exact
toolchain, argument, environment, feature and dependency identity. Preparation
and commit rerun full resolution, while intermediate checks rehash the already
discovered paths with the resolver's generated-state exclusions. Cache and
output paths inside watched Cargo roots are accepted only when one of those
exact exclusions covers them.

Caller-owned shared targets remain outside automatic retention. Explicit
inspection takes their existing cross-process lock and reports canonical path,
logical size, last recorded build use and lock wait without removing state.

Acquisition-time retention remains opt-in. Callers may additionally select a
minimum interval; a policy-keyed atomic marker suppresses repeated scans for
the same policy while ensuring a changed policy runs immediately. The interval
applies to attempts, including nonfatal failures, and strict pruning remains
available independently.

Exact-sender snapshot capture and restore are part of the single
`PocketIcSnapshotExt` trait. Controller-fallback and exact-sender operations
remain distinct policies on that trait.

## PocketIC and diagnostics follow-ups

The same release may add independent additive improvements that do not alter
the cache contract:

- explicit per-canister snapshot senders alongside controller-fallback capture;
- compact `Display` output for cache and pool outcomes and timings;
- a closure-backed baseline recipe adapter that still requires every typed
  reset, readiness, validation, and failure-classification receipt.

Convenience APIs must not manufacture reset coverage or weaken the existing
pool isolation contract.

## Acceptance coverage

The implementation is complete only with tests proving:

- default isolated behavior produces the expected exact fingerprints;
- a source edit reuses shared Cargo incremental state but selects a new exact
  immutable entry;
- a later old fingerprint can be rematerialized without Cargo;
- two processes using one shared target cannot build concurrently;
- different cache roots sharing one incremental target still coordinate;
- an exact hit does not acquire or mutate the shared target;
- failed builds and changed inputs publish no reusable entry while preserving
  shared incremental state;
- retention removes immutable entries without touching the shared target;
- dynamic and non-UTF-8 arguments and environment values affect identity;
- strict Clippy, rustdoc, package verification, and the declared MSRV pass.

No consumer package names, Binaryen policy, `icp build` behavior, PocketIC
topology, or production Wasm behavior belongs in this feature.
