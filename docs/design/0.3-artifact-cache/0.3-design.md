# Content-Addressed Wasm Build Coordination

## Status

Accepted and implemented for the artifact API through `0.4.2`.

Consumer feedback after `0.3.5` is consolidated in
[`follow-up-design.md`](follow-up-design.md). That proposal keeps one generic
transactional cache underneath Cargo builds, external artifact sets, and
post-link transforms instead of adding parallel cache implementations.

## Decision

`ic-testkit` owns generic, exact coordination for repeated Cargo Wasm builds.
Downstream suites continue to own package selection, profiles, build-specific
environment, additional inputs, and the target directory.

`WasmBuildSpec` describes those caller choices. Resolution adds:

- the selected workspace packages and their resolved local dependency closure;
- package sources plus the workspace manifest, lockfile, Rust toolchain files,
  and effective Cargo configuration from the invocation-directory hierarchy,
  Cargo home, and recursive includes;
- the compilation target and ordered Cargo profile/feature arguments;
- Cargo and rustc version identity;
- explicit child environment overrides and selected inherited environment;
- caller-declared inputs read outside Cargo's package graph.

File names and contents are hashed with SHA-256. Modification times are never
part of the fingerprint. `WasmBuildRecord` exposes both the source/config input
digest and the complete build fingerprint so downstream diagnostics can
distinguish content changes from toolchain or environment changes.

## Coordination protocol

```text
WasmBuildSpec
  -> acquire target-directory process lock
  -> resolve toolchain + Cargo package graph
  -> hash exact declared inputs
  -> derive build fingerprint
  -> verify every artifact and per-artifact stamp
       -> match: record last use + Reused
       -> public miss + content-addressed artifact match:
            materialize + record last use + Reused
       -> complete miss: cargo build in fingerprint-specific target directory
           -> verify every artifact is nonempty
           -> verify inputs did not change during Cargo
           -> stamp the content-addressed artifacts
           -> atomically materialize caller-facing artifacts and stamps
           -> record last use
           -> Built
           -> any failure: remove the incomplete fingerprint directory
```

The process lock is scoped to the selected Cargo target directory. It
coordinates independent test binaries without imposing a host-wide build lock
or prescribing one global cache location.

Stamps sit beside their artifacts and contain both the build fingerprint and
the Wasm content digest. This detects cache corruption and outputs overwritten
outside the cache API. Per-artifact stamps are also required because different
specs can write the same Cargo output path: a successful build replaces that
artifact's current stamp, so an older fingerprint cannot later claim the
overwritten output. Exact builds live in fingerprint-specific Cargo target
directories beneath the caller's target directory, allowing an older exact
artifact to be materialized again without rerunning Cargo. A failed,
interrupted, incomplete, or input-racing build does not publish a successful
stamp. Once a fingerprint-specific target has been created, normal Rust error
returns remove it before returning to the caller. An unwind also triggers
best-effort cleanup. If an ordinary build failure and cleanup failure coincide,
`FailedBuildCleanup` retains the structured build failure and the I/O cleanup
failure.

## Cache lifecycle

Every target root used by a cached build or pruning pass receives a
standards-compliant `CACHEDIR.TAG`. This identifies the caller-selected target
as disposable cache data to cache-aware tools without changing ownership of
the path.

Successful builds and exact cache hits atomically update a last-use marker in
the fingerprint-specific target. `prune_wasm_build_cache` accepts a
`WasmBuildCachePrunePolicy` with optional maximum age and maximum logical size.
It removes over-age entries first, then removes least-recently-used entries
until the size limit is met. `WasmBuildCachePruneReport` exposes scanned,
removed, retained, before, removed, and retained counts and byte totals.

Pruning acquires the same target-directory process lock as builds, so it cannot
delete an active build directory. Recursive deletion is restricted to direct
children of `.ic-testkit/wasm-targets` whose names are exactly 64 hexadecimal
characters. Public Wasm outputs, lock files, unrelated Cargo outputs, and
unrecognized directories are not eligible. Logical file lengths are used for
portable size accounting; filesystem allocation and hard-link sharing can make
on-disk usage differ.

Callers can instead attach the policy to `WasmBuildSpec`. This runs retention
under the lock already held by the build acquisition and protects the active
fingerprint even when retaining it leaves the cache above the requested size or
age bound. Because the requested artifacts are already ready, this maintenance
is best-effort: the build record contains either the prune report or a rendered
maintenance failure, and its timing is reported separately.

## Input boundary

Cargo metadata identifies local source packages. Registry and Git dependency
identity remains anchored by `Cargo.lock` and Cargo's checksum/revision
validation rather than duplicating Cargo's source cache.

Build scripts can read arbitrary host state that Cargo metadata cannot infer.
Callers therefore declare application-specific inherited environment and
additional file trees on `WasmBuildSpec`. Undeclared host inputs are outside
the cache contract.

Cargo configuration discovery mirrors Cargo's search from the build invocation
directory through its ancestors and the effective Cargo home. The extensionless
`config` file wins when both supported names exist. Recursive string and table
`include` entries are followed, including optional-missing semantics. External
configuration locations contribute an opaque location digest because their base
path can affect relative configuration values.

The caller-selected target directory is the lock and artifact namespace. It is
not a global cache chosen by `ic-testkit`, preserving downstream control over
cleanup and CI persistence. Callers can opt into generic age/size retention
without ceding location or policy ownership.

## Exact generated-artifact freshness

`WatchedInputSnapshot` uses the same deterministic content hashing model for
non-Cargo generated artifacts. An artifact is fresh only when it is nonempty
and has a matching sidecar written by `mark_artifact_fresh` after a successful
build. Existing files without a content stamp are deliberately treated as
stale rather than falling back to filesystem timestamps.

## Timing boundary

Each `WasmBuildRecord` reports time spent waiting for the process lock, running
Cargo when needed, optional cache maintenance, and completing the whole
operation. Input resolution is further divided into tool identity, Cargo
metadata, input discovery, and content hashing while retaining the original
aggregate accessor. This keeps observation structured without selecting a
logging or tracing framework for downstream applications.
