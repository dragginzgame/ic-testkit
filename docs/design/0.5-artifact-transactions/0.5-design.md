# Transactional Artifact-Set Cache

## Status

Implemented for `0.5.0` after the released `0.4.2` Cargo-cache maintenance
work and hardened in `0.5.1`. The implementation preserves the correctness and
ownership boundaries in this document without adding consumer-specific command
policy.

## Problem

The exact Wasm cache owns Cargo compilation, but consumers also repeat
deterministic commands outside Cargo:

- IcyDB transforms one Cargo-built Wasm with a pinned Binaryen executable and
  ordered optimizer arguments.
- Canic invokes an external build pipeline that publishes a related root Wasm,
  role Wasms, and metadata as one logical result.

Both need the same primitive: lock one recipe, identify all effective inputs,
build into temporary storage, validate the complete output set, verify inputs
again, and publish or reuse the result as one transaction. `ic-testkit` must not
learn Binaryen flags, `icp build` commands, or application package names.

## Public model

The caller constructs an `ArtifactCacheSpec` containing:

- a caller-selected cache root;
- a stable namespace separating unrelated stores;
- a required caller-owned recipe identity, such as
  `icydb/wasm-opt/v1` or `canic/root-release-set/v1`;
- an optional coordination scope for commands sharing an external work tree;
- uniquely labeled input files or directories;
- optional tool files, ordered arguments, environment values, and additional
  opaque identity fields;
- uniquely named outputs, their public destinations, and built-in validation;
- optional age and logical-size retention.

Logical identifiers are cache identity. Filesystem destinations are not: two
checkouts can materialize the same exact result at different absolute paths.
Raw identifiers are never used as cache paths; their digests select namespaces
and lock files.

A declared input or tool may be an ancestor of the cache root so a caller can
hash a broader source tree, but it may not be located inside the cache root.
Output destinations must be outside the cache, resolve to distinct paths, and
must not equal or be nested within a declared input or tool. This prevents
cache-owned metadata from becoming a silently unkeyed input and prevents
materialization from mutating the inputs that selected an entry.

The initial output-validation contract supports regular files and nonempty
regular files. The nonempty policy is the default. Custom callbacks are not
stored in the spec because they make recipe identity and recovery difficult to
reason about. Consumers needing format-specific checks validate in their build
step before commit; later built-in validation variants must have explicit key
identity.

## Cache key

The content key includes:

- a versioned cache-format domain;
- namespace and recipe identity;
- stable labels plus exact contents of every declared input and tool path;
- ordered argument bytes;
- sorted environment names, including set/unset state and value bytes;
- sorted additional identity labels and bytes;
- sorted logical output names and validation policies.

Output destinations, cache-root paths, timestamps, and coordination scope do
not affect content identity. Coordination scope controls mutual exclusion, not
whether two recipes produce identical bytes. Secret environment values may be
hashed but are never rendered in `Debug`, errors, manifests, or diagnostics.

## Locking

Three lock levels have separate jobs:

1. A coordination-scope lock is held while the caller runs the external
   command. It serializes different keys that share mutable external state.
2. A content-key lock prevents two processes from building the same exact
   result concurrently, even if their coordination scopes differ.
3. A namespace lock protects short cache mutations: entry lookup,
   publication, materialization accounting, and pruning.

Locks are acquired in that order. The namespace lock is not held while the
external command runs. Builds write only to transaction-owned staging
directories, so namespace pruning cannot observe or remove partial work.

## Lifecycle

```text
prepare
  -> validate the spec
  -> write CACHEDIR.TAG
  -> acquire coordination lock
  -> capture exact inputs and derive the content key
  -> acquire content-key lock
  -> verify inputs did not change while waiting
  -> acquire namespace lock
  -> validate manifest plus every cached output digest
       -> valid: atomically materialize all destinations, verify inputs again,
                 record last use, optionally prune, return Reused
       -> absent/corrupt: remove only that exact entry, create staging,
                          return an owned build transaction

caller build
  -> execute any command outside ic-testkit
  -> write directly to named staging outputs or import fixed external outputs

commit
  -> validate every staged output
  -> recapture inputs and reject any change
  -> digest every output and write the complete manifest last in staging
  -> acquire namespace lock
  -> atomically rename staging to the immutable content entry
  -> atomically materialize caller destinations
  -> record last use and optionally prune while protecting the active entry
  -> return Built

drop/error/panic
  -> remove uncommitted staging data
  -> never publish a reusable manifest
```

The caller runs the command. A transaction exposes a staging directory, a
checked staging path for each logical output, and an import helper for commands
whose output location cannot be redirected. `commit` consumes the transaction.

## Manifest and corruption handling

A committed entry is immutable and contains:

- one cache-format version;
- its full content key;
- the sorted logical output schema;
- each output's logical length and SHA-256 digest;
- output files stored under cache-owned index names;
- a last-use marker excluded from content identity.

No other entry-root children are valid. Before publication, staging contains
only its cache-owned `outputs` directory; a command that leaves logs or other
files beside that directory must remove or relocate them before commit.

The manifest is published last before the staging directory is renamed. A hit
recomputes every output digest and validates the complete expected manifest.
Missing, empty, extra-schema, malformed, non-directory, or content-mismatched
entries are cache misses and are removed under the namespace lock. Manifests
are compared as bytes, so invalid text encoding is ordinary recoverable
corruption. An inability to inspect or remove a corrupt entry is a structured
cache error, not silent reuse.

Caller-facing destinations are streamed through same-directory temporary files
and atomic renames. Hashing and fixed-output imports are likewise streamed so
memory use does not scale with total artifact bytes. The operation returns only
after every destination has been materialized. A materialization error can
leave some ordinary destination files updated, but never makes an incomplete
cache entry reusable; retrying the same spec repairs the destinations from the
committed entry.

## Input races and failure semantics

Inputs are captured before returning a build transaction and again during
commit. A mismatch returns `InputsChangedDuringBuild` and deletes staging.
Reuse similarly verifies inputs after lock waits and after materialization; a
race retries resolution instead of returning an artifact for a stale snapshot.

Normal commit failures remove staging before returning. If both the operation
and cleanup fail, the error retains both causes. Dropping or unwinding through
an uncommitted transaction performs best-effort cleanup without hiding the
caller's panic.

Typed outcomes are `Built` and `Reused`. Records expose the content key, input
digest, materialized paths, phase timings, and optional nonfatal maintenance
outcome. Cache maintenance cannot turn an otherwise successful acquisition
into a failure.

## Retention

The generic cache reuses the existing optional maximum-age and maximum-logical-
size policy. Pruning operates on complete direct child entries only, removes
over-age entries before least-recently-used size eviction, and protects the
entry being built or reused. Staging and lock directories are never counted as
committed entries. Ordinary drops remove staging immediately, and the next
acquisition of the same content key removes staging abandoned by a terminated
process. Configured and explicit retention also try each abandoned staging
directory's content-key lock without blocking and remove it only when no active
transaction owns that key. Reports account for reclaimed uncommitted
directories and bytes separately from committed entries. Persistent empty lock
files remain coordination metadata.

The existing Wasm cache keeps its public API and on-disk layout. Shared tag,
locking, last-use, directory measurement, and retention primitives move under
both APIs before the new transaction surface is considered complete. A later
adapter may move Cargo builds onto the full artifact transaction, but `0.5.0`
does not require an on-disk migration or invalidate `0.4.x` Wasm entries.

## Observability

Timings report:

- coordination and content-key lock wait;
- input capture and verification;
- cache lookup and validation;
- caller build interval for a committed transaction;
- staged-output validation and publication;
- caller-destination materialization;
- optional maintenance;
- total acquisition time.

The API records durations but does not choose a logging or tracing framework.

## Acceptance coverage

The implementation is complete only with tests for:

- one input and one transformed output;
- one transaction publishing several outputs;
- exact reuse without invoking a build;
- argument, environment, recipe, tool, and input invalidation;
- public destinations outside the cache root;
- rejection of cache-local declared inputs, destination aliases, and
  input/output overlap;
- missing, empty, tampered, and partially staged outputs;
- malformed manifest bytes, non-directory entries, and unexpected root files;
- changed inputs during a build;
- abandoned and panicked transactions;
- pruning that removes orphan staging while protecting an active transaction;
- overlapping processes or threads for the same content key;
- independent keys sharing a coordination scope;
- cache corruption recovery;
- age/size pruning with active-entry protection;
- checkout-root independence for stable logical inputs;
- streaming digest equivalence with the monolithic `v1` cache-key calculation;
- strict Clippy, rustdoc, package verification, and the declared MSRV.

No PocketIC instance, canister topology, production Wasm behavior, or
application-specific command policy is part of this feature.
