# Independent Artifact Orchestration and Build Progress

## Status

Implemented for the unreleased `0.7` API after `0.6.1`. This design is
additive. Existing single-spec Wasm and transactional cache calls preserve
their behavior and remain silent unless a caller selects an observation API.

## Problem

Consumers now use exact Wasm and transactional caches for many related build
variants. Three generic gaps remain:

- building several Cargo packages in one normal Cargo command can unify shared
  dependency features, while callers need each variant's standalone feature
  resolution;
- legitimate cold Cargo builds can run for more than a minute with no visible
  activity;
- callers repeat safe sequential acquisition and cleanup logic for several
  independent post-link transactions.

The shared incremental Cargo target introduced in `0.6` also needs explicit
bounded maintenance. It is mutable caller-owned compilation state, so immutable
fingerprint-entry pruning cannot safely treat its internal directories as
independent LRU entries.

## Goals

- Orchestrate several independent `WasmBuildSpec` values without changing any
  spec's Cargo feature semantics.
- Expose opt-in phase, output, heartbeat, and completion events for a Wasm
  acquisition.
- Safely orchestrate several independent `ArtifactCacheSpec` transactions
  without holding multiple build locks at once.
- Permit caller-triggered age/size cleanup of shared incremental targets under
  the existing cross-process lock.
- Keep all APIs package-, tool-, and application-agnostic.

## Non-goals

- One Cargo invocation for several Wasm specs.
- Parallel batch execution or a new task runtime.
- Atomic publication across independent cache specs.
- Automatic cleanup of caller-owned shared incremental targets.
- Inferring which internal Cargo target subdirectories are independently
  disposable.
- Consumer-specific Binaryen, ICP, package, or topology policy.

## Independent Wasm batch

`build_wasm_canisters_cached_batch` accepts an ordered slice of complete
`WasmBuildSpec` values. It runs the ordinary single-spec acquisition once per
entry, sequentially and fail-fast.

This is intentionally not implemented as `cargo build -p a -p b`. Cargo may
unify features of shared dependencies across the selected packages. Separate
commands retain each entry's package set, profile arguments, environment,
dependency closure, exact fingerprint, cache mode, locks, and retention
policy.

On success, `WasmBuildBatchOutcome` returns outcomes in specification order and
the total wall-clock duration. On failure, `WasmBuildBatchError` identifies the
failed index, preserves the successful prefix, reports elapsed time, and owns
the original `WasmBuildError`. Earlier immutable publications and materialized
outputs remain valid.

The batch is not parallel. Shared incremental targets already serialize their
mutable state, and isolated specs can have unrelated resource constraints.
Callers that need parallelism can schedule independent single-spec calls with
an application-appropriate executor.

## Progress observation

`build_wasm_canisters_cached_with_progress` preserves the result and failure
contract of the silent function while synchronously delivering structured
events. Events cover:

- acquisition start;
- every exact input-resolution pass;
- cache miss and hit;
- shared-target lock start and acquisition;
- Cargo start;
- raw stdout and stderr chunks;
- quiet-period Cargo heartbeats;
- Cargo exit status and duration;
- final built or reused outcome.

`WasmBuildProgressConfig` defaults to raw output forwarding plus a ten-second
heartbeat. Callers may disable output forwarding or heartbeats independently.
Output is always captured internally so `CommandFailed` retains complete lossy
diagnostics as before. Forwarded chunks use raw bytes and retain per-stream
read order; relative ordering between stdout and stderr is inherently
scheduler-dependent.

Observers execute synchronously on the acquisition thread. They must avoid
slow or reentrant cache operations. If an observer panics while Cargo is live,
an owned child guard kills and waits for Cargo during unwinding. Existing lock
RAII and incomplete-entry cleanup then run normally. Observer panics are not
translated into cache failures.

The batch progress API wraps each single-build event with its specification
index. It does not replace or coarsen standalone progress.

## Independent transactional batch

`build_artifact_caches_batch` accepts ordered `ArtifactCacheSpec` values and a
population callback. Preparation is sequential. Exact hits append a reused
outcome without invoking the callback. A miss lends the callback one
`ArtifactBuildTransaction`; a successful callback commits it before the next
spec is prepared.

Holding at most one transaction avoids self-deadlock when several recipes use
the same coordination scope or mutable external builder. A callback error
synchronously aborts the active transaction and reports any cleanup failure
alongside the caller error. A panic relies on the transaction's existing
panic-safe `Drop` cleanup and continues unwinding.

The batch is explicitly not atomic across specs. Successful prefix entries
remain published if a later preparation, callback, or commit fails. A pipeline
requiring all-or-nothing publication must declare all outputs on one
`ArtifactCacheSpec`; that existing transaction is the atomic batch primitive.

## Shared incremental target maintenance

`maintain_shared_incremental_target` applies an explicit age and/or logical
size policy under the same canonical target lock used by builds. A missing
target returns `None` without creating state. A retained or cleared target
reports:

- canonical path;
- logical bytes before and after;
- prior recorded use time;
- whether clearing occurred;
- lock wait and maintenance durations.

A shared Cargo target has no stable content-addressed sub-entry boundary.
Therefore exceeding either threshold clears every other direct child. Callers
must not colocate unrelated data that needs to survive a clear. Maintenance
preserves the target root, `CACHEDIR.TAG`, and `.ic-testkit` lock directory.
Keeping the existing lock inode reachable is essential: removing it while its
file descriptor is locked could let another process create and acquire a
replacement lock before maintenance finishes.

Before acquiring the maintenance lock, the ordinary exact Cargo resolver
validates the complete spec and rejects a shared target that overlaps package
sources, configuration, or caller-declared additional inputs. The overlap
check covers both a target nested within an input and a dangerously broad
target containing an input.

After clearing, the target's use marker is refreshed. A failed partial clear
returns a structured filesystem error while still holding the lock through
unwinding. Exact immutable outputs are outside this target and remain
untouched.

Maintenance is never acquisition-time default behavior. The shared target is
caller-owned, and clearing it can make the next exact miss cold. Consumers
choose policy thresholds and invocation cadence appropriate to local disk and
CI cache constraints.

## Acceptance coverage

Focused coverage must prove:

- two specs with incompatible standalone dependency features both build in one
  independent batch;
- an invalid entry reports its exact batch index;
- observed Cargo forwards raw stdout and stderr and emits heartbeats during a
  quiet interval;
- a zero heartbeat interval is rejected before build work;
- transactional specs sharing a coordination scope build and then reuse in
  order without deadlock;
- a callback error cleans the current transaction and retains the successful
  prefix;
- shared-target size maintenance clears Cargo state while preserving the cache
  tag and original coordination lock path.

The final release gate additionally covers formatting, Clippy with warnings
denied, rustdoc warnings, packaging, the declared MSRV, and existing repository
tests under the maintainer's release workflow.
