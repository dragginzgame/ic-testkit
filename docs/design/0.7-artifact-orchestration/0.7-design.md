# Independent Artifact Orchestration and Build Progress

## Status

Implemented for the unreleased `0.7` API after `0.6.1`. Single-spec Wasm and
transactional cache calls remain silent unless a caller selects an observation
API. Pre-`1.0` API changes are hard cuts rather than parallel entry points.

## Problem

Consumers now use exact Wasm and transactional caches for many related build
variants. Three generic gaps remain:

- building several Cargo packages in one normal Cargo command can unify shared
  dependency features, while callers need each variant's standalone feature
  resolution;
- legitimate cold Cargo builds can run for more than a minute with no visible
  activity;
- callers repeat safe sequential acquisition and cleanup logic for several
  independent post-link transactions.

The shared incremental Cargo target introduced in `0.6` also needs explicit
bounded maintenance. It is mutable caller-owned compilation state, so immutable
fingerprint-entry pruning cannot safely treat its internal directories as
independent LRU entries.

## Goals

- Orchestrate several independent `WasmBuildSpec` values without changing any
  spec's Cargo feature semantics.
- Expose opt-in phase, output, heartbeat, and completion events for a Wasm
  acquisition.
- Safely orchestrate several independent `ArtifactCacheSpec` transactions
  without holding multiple build locks at once.
- Permit caller-triggered age/size cleanup of shared incremental targets under
  the existing cross-process lock.
- Keep all APIs package-, tool-, and application-agnostic.

## Non-goals

- One Cargo invocation for several Wasm specs.
- Parallel batch execution or a new task runtime.
- Atomic publication across independent cache specs.
- Automatic cleanup of caller-owned shared incremental targets.
- Inferring which internal Cargo target subdirectories are independently
  disposable.
- Consumer-specific Binaryen, ICP, package, or topology policy.

## Independent Wasm batch

`build_wasm_canisters_cached_batch` accepts an ordered slice of complete
`LabeledWasmBuildSpec` values. Labels are required, nonempty, unique, and
retained in canonical ordered entries, outcomes, failures, progress, and
integrated maintenance results. They are report identity only and do not alter
the underlying exact Wasm fingerprint. Invalid labels reject the complete
batch before metadata resolution, progress, or build work. The batch runs the
ordinary single-spec acquisition once per entry, sequentially, and retains
every result.

This is intentionally not implemented as `cargo build -p a -p b`. Cargo may
unify features of shared dependencies across the selected packages. Separate
commands retain each entry's package set, profile arguments, environment,
dependency closure, exact fingerprint, cache mode, locks, and retention
policy.

`WasmBuildBatchReport` retains one canonical labeled entry for every
specification, continues after independent failures, exposes structured
labeled outcome and failure iterators, reports total wall-clock duration, and
retains per-entry elapsed time for successful and failed acquisitions.
Successful immutable publications and materialized outputs remain valid when
another entry fails. Detailed phase timings remain available on successful
build records. Retaining partial phase timings on failures is deferred because
the current error variants do not own the acquisition progress recorder;
adding it is a broader error-contract hard cut rather than a small report
completion.

Specifications with the same workspace, tool environment, and
metadata-affecting arguments share one input-resolution snapshot. Tool
identity and Cargo metadata run once, and composable per-root content digests
are memoized across package closures. Each specification still receives the
same exact fingerprint it would receive standalone. Incompatible resolution
contexts use separate snapshots instead of conflating feature graphs.

Incompatible feature/metadata groups currently own separate digest caches even
inside one batch. A future explicit batch-scoped immutable-source lease could
share content digests across those groups without sharing their Cargo metadata
or dependency graphs. Creating that lease must require the caller to hold the
external write exclusion covering every source/configuration/tool input until
the batch returns. A validated-snapshot alternative may recheck identity and
discovery boundaries, but any file content it rehashes is validation work, not
digest reuse. The measured warm cost remains roughly 370--395 ms for one local
canister and several seconds across a consumer fleet, so this stays a concrete
optimization target rather than an ambient cache proposal.

### Deferred cross-call immutable build session

Input reuse in `0.8.x` ends when the batch call returns. There is no hidden
process-global resolver and no public cross-call session. The acquisition path
currently proves exact-cache freshness by reading current inputs; silently
retaining content digests across calls would allow a source edit to reuse a
stale fingerprint.

A future cross-call API must therefore be an explicitly owned, sequential
`WasmBuildSession`, not ambient state. Its constructor must require a staleness
policy rather than selecting one implicitly. The high-reuse policy would be a
caller-guaranteed immutable-source lease covering Cargo/rustc executable
identity, Cargo configuration and manifests, discovered source inputs,
caller-declared inputs, and relevant environment for the complete session
lifetime. Any mutation invalidates the lease; the caller must hold the external
write exclusion that makes that promise true. A verification policy may instead
revalidate before each batch, but it cannot claim content-digest reuse for the
files it rehashes.

Within a valid immutable lease, compatibility grouping would use the same
workspace/tool/environment and metadata-affecting argument boundaries as the
current batch resolver. The session would expose aggregate resolution run/reuse
counters, remain sequential, and never combine Cargo package builds. It must
also provide explicit invalidation or consumption after a detected input race.
The current release has no lifetime or write-exclusion token capable of
enforcing those obligations, so this contract is documented rather than
partially implemented. This keeps the 23-acquisition/10-identity consumer case
visible without weakening exact-cache correctness to remove its measured input
resolution cost.

The batch is not parallel. Shared incremental targets already serialize their
mutable state, so parallelizing those entries would primarily add lock
contention. Any future built-in parallel mode must be limited to isolated
target directories and justified by benchmarks before becoming API. Callers
that already have measurements can schedule isolated single-spec calls with an
application-appropriate bounded executor.

## Progress observation

`build_wasm_canisters_cached_with_progress` preserves the result and failure
contract of the silent function while synchronously delivering structured
events. Events cover:

- acquisition start;
- every exact input-resolution pass;
- cache miss and hit;
- shared-target lock start and acquisition;
- Cargo start;
- raw stdout and stderr chunks;
- quiet-period Cargo heartbeats;
- Cargo exit status and duration;
- final built or reused outcome.

`WasmBuildProgressConfig` defaults to raw output forwarding plus a ten-second
heartbeat. Callers may disable output forwarding or heartbeats independently.
Output is always captured internally so `CommandFailed` retains complete lossy
diagnostics as before. Forwarded chunks use raw bytes and retain per-stream
read order; relative ordering between stdout and stderr is inherently
scheduler-dependent.

Observers execute synchronously on the acquisition thread. They must avoid
slow or reentrant cache operations. If an observer panics while Cargo is live,
an owned child guard kills and waits for Cargo during unwinding. Existing lock
RAII and incomplete-entry cleanup then run normally. Observer panics are not
translated into cache failures.

The batch progress API wraps each single-build event with its caller label and
specification index. It does not replace or coarsen standalone progress.

## Independent transactional batch

`build_artifact_caches_batch` accepts ordered `LabeledArtifactCacheSpec` values
and a population callback. Labels are required, nonempty, unique, and retained
through the callback and every ordered report entry. They are composition
identity only and do not alter artifact cache keys. Invalid label structure
rejects the complete batch before any cache work starts. Preparation is
sequential. Exact hits append a reused outcome without invoking the callback. A
miss lends the callback its stable label and one `ArtifactBuildTransaction`; a
successful callback commits it before the next spec is prepared.

Holding at most one transaction avoids self-deadlock when several recipes use
the same coordination scope or mutable external builder. A callback error
synchronously aborts the active transaction and reports any cleanup failure
alongside the caller error. The ordered `ArtifactCacheBatchReport` retains that
indexed failure and continues with later independent specifications. A panic
relies on the transaction's existing panic-safe `Drop` cleanup and continues
unwinding.

The batch is explicitly not atomic across specs. Successful entries remain
published when another preparation, callback, or commit fails. A pipeline
requiring all-or-nothing publication must declare all outputs on one
`ArtifactCacheSpec`; that existing transaction is the atomic batch primitive.
The report's metrics aggregate built/reused/failed counters and successful
acquisition timings without adding another event stream. Ordered entries are
the canonical report surface; parallel result, label, and elapsed sidecars are
not retained. Outcome and failure views carry the label, original index, and
wall time. Failures retain the primary phase plus partial preparation,
callback, explicit abort cleanup, and commit timings. Commit timing includes
cleanup performed internally by a failed `ArtifactBuildTransaction::commit`.

Generic input hashing is intentionally not memoized across entries today.
Preparation repeatedly hashes declared inputs to detect mutation before cache
reuse or publication. A future shared-digest batch context must therefore
require a caller-supplied source-immutability lease or perform explicit
revalidation; silently reusing a digest for merely matching paths is unsound.

### Dependency-closure fingerprint precision

The Wasm resolver derives cache identity from a validated semantic projection
of Cargo metadata rather than directly hashing the complete workspace manifest
and lockfile. The projection includes every package in the selected resolve
closure, enabled features, dependency names and target/kind conditions, exact
external source/checksum/revision identities, effective build-relevant package
fields, workspace profiles, resolver and lint settings, selected local package
contents, toolchain/configuration, and caller-declared inputs. A host-only
workspace dependency or lockfile update that leaves that projection unchanged
therefore retains the selected Wasm key.

This narrower identity does not narrow mutation validation. Resolution also
retains the complete manifest, lockfile, selected source roots, configuration,
toolchain files, and additional inputs under a separate conservative digest.
Cargo builds and attached external artifact transactions compare that raw
digest before and after their operation and abort publication on any mismatch,
including one that is semantically unrelated. A selected package rooted at the
workspace root, or a local package that cannot be normalized beneath it, uses
the complete manifest/lockfile identity as a conservative fallback.

Build scripts, procedural macros, and source-level includes may read files or
environment outside Cargo's graph. Those remain caller-declared additional
inputs/environment; the projection does not infer arbitrary host reads. This is
a process-local resolution operation, not an ambient or cross-call cache.

## Shared incremental target maintenance

`maintain_shared_incremental_target` applies an explicit age and/or logical
size policy under the same canonical target lock used by builds. A missing
target returns `None` without creating state. A retained or cleared target
reports:

- canonical path;
- logical bytes before and after;
- prior recorded use time;
- whether clearing occurred;
- lock wait and maintenance durations.

A shared Cargo target has no stable content-addressed sub-entry boundary.
Therefore exceeding either threshold clears every other direct child. Callers
must not colocate unrelated data that needs to survive a clear. Maintenance
preserves the target root, `CACHEDIR.TAG`, and `.ic-testkit` lock directory.
Keeping the existing lock inode reachable is essential: removing it while its
file descriptor is locked could let another process create and acquire a
replacement lock before maintenance finishes.

Before acquiring the maintenance lock, the ordinary exact Cargo resolver
validates the complete spec and rejects a shared target that overlaps package
sources, configuration, or caller-declared additional inputs. The overlap
check covers both a target nested within an input and a dangerously broad
target containing an input.

After clearing, the target's use marker is refreshed. A failed partial clear
returns a structured filesystem error while still holding the lock through
unwinding. Exact immutable outputs are outside this target and remain
untouched.

Maintenance is never acquisition-time default behavior. The shared target is
caller-owned, and clearing it can make the next exact miss cold. Consumers
choose policy thresholds and invocation cadence appropriate to local disk and
CI cache constraints.

## Acceptance coverage

Focused coverage must prove:

- two specs with incompatible standalone dependency features both build in one
  independent batch;
- an invalid entry reports its exact batch index and does not prevent later
  entries from running;
- observed Cargo forwards raw stdout and stderr and emits heartbeats during a
  quiet interval;
- a zero heartbeat interval is rejected before build work;
- transactional specs sharing a coordination scope build and then reuse in
  order without deadlock;
- a callback error cleans the current transaction, retains its indexed failure,
  and does not prevent later independent entries from running;
- shared-target size maintenance clears Cargo state while preserving the cache
  tag and original coordination lock path.

The final release gate additionally covers formatting, Clippy with warnings
denied, rustdoc warnings, packaging, the declared MSRV, and existing repository
tests under the maintainer's release workflow.
