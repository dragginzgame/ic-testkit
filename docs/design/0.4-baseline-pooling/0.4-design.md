# Bounded Multi-Canister Baseline Pool

## Status

Implementation in progress for the unreleased `0.4` API. The generic pool,
structurally owned recipe contract, typed reset evidence, outcomes, recovery
semantics, runtime scheduler, and standalone-pool scheduler migration are now
implemented. Generic coverage now exercises time, cycle, and extra-canister
mutation one domain at a time and recovery from a killed test-owned server. The
public API also has a compile-checked two-canister consumer recipe, including
exact baseline-derived restore evidence and dead-transport classification. The
downstream Canic pilot and realistic capacity/RSS benchmarks remain follow-up
work.

## Motivation

`CachedPocketIcBaseline<T>` already owns one PocketIC instance, a deterministic
set of canister snapshots, and caller metadata. It can amortize a multi-canister
topology, but its current helper uses one caller-provided `Mutex` slot. A
bounded pool would add lazy capacity, independent slots, and reusable lifecycle
handling without pretending that restoring canister snapshots rewinds all
PocketIC state.

Canic is a sufficient initial consumer:

- its root topology is expensive to construct and already has domain-specific
  restore and readiness logic;
- capacity one can amortize that setup across sequential tests immediately;
- selected read-only or snapshot-contained tests can later use capacity two if
  they share a test binary and Canic relaxes `--test-threads=1` for that slice.

IcyDB's current SQL matrix already receives the relevant benefit from the
standalone single-canister pool. It is not an initial multi-canister-pool
consumer.

## Non-claim

This pool does not provide fresh-PocketIC isolation. A canister snapshot does
not inherently rewind:

- PocketIC time, timers, or pending messages;
- canisters created or deleted after the baseline;
- canister-ID allocation heads;
- subnet metrics, routing, or other subnet-global state;
- cycle accounting outside the declared restoration policy;
- external files, processes, or services used by the fixture.

The pool returns a reused lease only after a recipe has restored, reset,
quiesced, and validated its declared baseline. State outside that contract is
not silently treated as reset.

## Decision summary

1. The primary pool has runtime capacity through `NonZeroUsize`.
2. One pool structurally owns one recipe value for its complete lifetime.
3. The recipe supplies a caller-owned stable `FixtureRecipeId` and every
   lifecycle operation.
4. Reset requirements and achieved reset receipts are typed and checked before
   a reused lease is returned.
5. Built and restored slots pass the same final invariant validation.
6. Recoverable preparation failure invalidates a slot and permits one rebuild;
   recovery failure retains both errors.
7. Panics are never converted into cache misses. The slot is invalidated and
   the panic continues.
8. Standalone and multi-canister pools share one internal bounded slot/lease
   scheduler.

## Public boundary

Names are illustrative, but the ownership shape is intentional:

```rust,ignore
pub struct CachedPocketIcBaselinePool<R>
where
    R: PocketIcBaselineRecipe,
{
    recipe: R,
    // shared bounded-slot scheduler and lazily populated slots
}

impl<R> CachedPocketIcBaselinePool<R>
where
    R: PocketIcBaselineRecipe,
{
    pub fn new(capacity: NonZeroUsize, recipe: R) -> Self;

    pub fn acquire(
        &self,
    ) -> Result<
        (
            CachedPocketIcBaselinePoolGuard<'_, R>,
            BaselinePoolOutcome,
        ),
        BaselinePoolError<R::Error>,
    >;
}
```

The recipe is not passed to `acquire`. It cannot silently change between
acquisitions, and a recipe mismatch cannot trigger rebuilding. The opaque
`FixtureRecipeId`, such as `canic/root-topology/v1`, remains useful in
diagnostics and receipts but is caller-owned rather than incompletely derived
from Wasm, arguments, or topology.

Runtime capacity is the primary API because full PocketIC topologies have
material and environment-dependent memory cost. Static users can still write:

```rust,ignore
static ROOT_POOL: OnceLock<CachedPocketIcBaselinePool<RootRecipe>> =
    OnceLock::new();

let pool = ROOT_POOL.get_or_init(|| {
    CachedPocketIcBaselinePool::new(NonZeroUsize::new(capacity()).unwrap(), root_recipe())
});
```

A const-capacity wrapper may be added later if it delegates to the same
implementation. It must not introduce a second scheduler.

## Recipe contract

The recipe owns application-specific behavior while the pool owns ordering,
capacity, slot state, recovery, and reporting:

```rust,ignore
pub trait PocketIcBaselineRecipe: Send + Sync + 'static {
    type Metadata: Send + 'static;
    type Error: std::error::Error + Send + Sync + 'static;

    fn id(&self) -> &FixtureRecipeId;
    fn reset_requirements(&self) -> &ResetRequirements;

    fn build(
        &self,
    ) -> Result<CachedPocketIcBaseline<Self::Metadata>, Self::Error>;

    fn restore_canisters(
        &self,
        baseline: &CachedPocketIcBaseline<Self::Metadata>,
    ) -> Result<CanisterRestoreReceipt, Self::Error>;

    fn reset_non_snapshot_state(
        &self,
        baseline: &CachedPocketIcBaseline<Self::Metadata>,
    ) -> Result<ResetReceipt, Self::Error>;

    fn drive_to_readiness(
        &self,
        baseline: &CachedPocketIcBaseline<Self::Metadata>,
    ) -> Result<ReadinessReceipt, Self::Error>;

    fn validate(
        &self,
        baseline: &CachedPocketIcBaseline<Self::Metadata>,
        preparation: &PreparedBaseline,
    ) -> Result<ValidationReceipt, Self::Error>;

    fn classify_failure(
        &self,
        stage: BaselinePreparationStage,
        error: &Self::Error,
    ) -> FailureDisposition;
}
```

Canic's root-specific waits remain inside its recipe. `ic-testkit` must not
learn Canic roles, registry state, billing rules, or readiness methods.

The exact trait may consolidate error types or receipts after implementation
prototyping. It must not consolidate the preparation stages: stage identity is
required for recovery policy, timings, and diagnostics.

## Typed reset coverage

Reset coverage is a runtime-enforced recipe attestation. Rust types cannot
independently prove simulator state, but the pool can refuse reuse unless the
successful hooks return achievements satisfying every declared requirement and
final validation succeeds.

Requirements and achievements use a closed set of domain kinds rather than
free-form strings:

```rust,ignore
pub enum ResetDomainKind {
    CanisterSnapshots,
    CanisterCycles,
    PocketIcTime,
    ExtraCanisters,
    PendingMessages,
    SubnetState,
    ExternalResources,
}

pub struct ResetRequirements {
    domains: BTreeMap<ResetDomainKind, ResetRequirement>,
}

pub struct ResetReceipt {
    achieved: BTreeMap<ResetDomainKind, ResetAchievement>,
}
```

Policies remain domain-specific. In particular:

```rust,ignore
pub enum CycleResetPolicy {
    PreserveCurrent,
    TopUpTo(u128),
    RestoreExactBaseline,
    RebuildOnMutation,
}

pub enum TimeResetPolicy {
    PreserveCurrent,
    RestoreBaseline,
    RebuildOnMutation,
}

pub enum ExtraCanisterPolicy {
    RequireBaselineSet,
    RemoveTracked,
    RebuildOnChange,
}

pub enum StateResetPolicy {
    ResetByRecipe,
    ValidateUnchanged,
    IrrelevantByRecipeContract,
    RebuildOnChange,
}
```

`PreserveCurrent` means the recipe does not proactively add or remove cycles
before restore; PocketIC may still charge for restoration. It is an explicit
allowance, not a claim that the baseline balance was restored. `TopUpTo` is not
equivalent to an exact cycle balance. A recipe that requires exact restoration
but cannot perform it must select rebuild-on-change or remain ineligible for
pooling.

Snapshot receipts identify the captured canister set and the cycle policy
actually applied. The pool checks that set against the baseline's captured
canister ids. Every recipe must declare snapshot and cycle requirements; other
domains are added when relevant to its reuse guarantees. The final validation
hook receives the complete preparation evidence and returns the recipe identity
plus a caller-defined invariant identity. Receipts must never contain secret
values.

After restoring a baseline, recipes should construct this evidence with
`CanisterRestoreReceipt::try_from_baseline`. The helper derives the exact set
from the baseline rather than requiring application metadata to duplicate the
canister ids for contract reporting. The explicit `try_new` constructor remains
available for custom validation and negative tests.

Deleting extra canisters is insufficient evidence of full reset because it
does not necessarily rewind allocation, metrics, queues, time, or cycles. A
recipe must declare those effects irrelevant, validate them, reset them through
supported APIs, or invalidate and rebuild the slot.

## Preparation protocol

Every slot is `Vacant`, `Preparing`, `Ready`, `Leased`, or `Invalid`.

### Vacant slot

```text
reserve slot
  -> build baseline
  -> validate built baseline invariants
  -> verify validation receipt carries the pool recipe identity
  -> return lease with Built outcome
```

The built path runs the same final validation used by restoration. This avoids
different guarantees for cold and warm leases.

### Ready slot

```text
reserve slot
  -> restore every captured canister
  -> apply non-snapshot reset domains
  -> drive topology to quiescence/readiness
  -> check achieved receipt against required coverage
  -> validate baseline invariants
  -> return lease with Restored outcome
```

No lease becomes visible between stages. A requirement/receipt mismatch is a
preparation failure, not a warning.

### Invalid slot

An invalid slot drops its stale baseline with teardown panics contained, then
follows the vacant-slot protocol. Successful recovery returns `Rebuilt` with
the reason that invalidated the old slot.

## Outcomes and timings

```rust,ignore
pub enum BaselinePoolOutcome {
    Built {
        slot: usize,
        timings: PoolTimings,
    },
    Restored {
        slot: usize,
        timings: PoolTimings,
    },
    Rebuilt {
        slot: usize,
        reason: RebuildReason,
        timings: PoolTimings,
    },
}
```

`PoolTimings` reports queue wait, build, snapshot restore, non-snapshot reset,
readiness, validation, stale teardown, and total duration. Non-applicable
phases are `None`. Successful outcomes carry complete timings, while
`BaselinePoolError::timings` retains the partial or combined timings recorded
before initial, fatal, or recovery failure. Slot indices are diagnostic only
and are not stable fixture identity.

Initial rebuild reasons include:

- dead PocketIC transport;
- snapshot restore failure;
- non-snapshot reset failure;
- readiness failure;
- reset coverage mismatch;
- invariant validation failure;
- explicit lease invalidation;
- unwind while a lease was held.

## Failure and panic semantics

Build failure leaves a vacant slot and returns the structured failure. It is
not retried automatically.

For a reused slot, a recoverable restore, reset, readiness, coverage, or
validation failure:

1. invalidates the slot;
2. preserves the original stage and error;
3. rebuilds at most once;
4. validates the rebuilt baseline;
5. returns `Rebuilt` on success;
6. returns a combined `RecoveryFailed { original, rebuild }` error on failure.

Both `Preparation` and `RecoveryFailed` errors retain total and completed phase
timings. Recovery failure timings cover the original preparation, stale-slot
teardown, and the failed rebuild, allowing consumers to measure failure
latency without wrapping acquisition in a second timer.

The recipe's failure classification may mark deterministic configuration or
contract failures as fatal instead of rebuilding. Recipe identity mismatch is
always caller misuse and never a rebuild reason. Structural recipe ownership
makes such mismatch impossible through the ordinary acquisition API.

Caller panics are not classified as failures. If a recipe hook panics, the
pool marks the reserved slot invalid, releases scheduler state, and resumes the
same unwind. If test code panics while holding a lease, guard drop detects
`std::thread::panicking()`, invalidates the slot, releases it, and permits the
assertion panic to continue. The next acquisition rebuilds that slot.

The guard also exposes explicit invalidation for tests that knowingly perform
state outside the recipe's reusable coverage.

## Shared bounded-slot scheduler

An internal `BoundedSlotPool<T>` owns scheduling only:

- runtime nonzero capacity;
- lazy slot creation;
- FIFO waiter tickets and an available-slot queue;
- no coordinator lock held while building, restoring, validating, or running
  test code;
- condition-variable checks under one mutex, preventing lost wakeups;
- poison recovery;
- panic-safe lease release;
- explicit slot invalidation and lazy rebuilding.

Only an index removed from the available queue may be prepared or leased. A
lease guard returns or invalidates that index exactly once on drop. Cancellation
guards remove abandoned waiter tickets so one interrupted waiter cannot block
the queue.

`CachedStandaloneCanisterFixturePool` and
`CachedPocketIcBaselinePool` should delegate to this primitive. Standalone
acquisition returns the structured lifecycle outcome directly. There must not
be two independent condition-variable implementations.

## Capacity and process boundary

The pool is process-local. Capacity greater than one creates potential
overlap, not parallelism by itself. Consumers also need:

- tests in the same process/test binary;
- test runner threads greater than one or explicit worker threads;
- enough CPU, memory, ports, and PocketIC server capacity.

Canic currently runs tests with `--test-threads=1`. Its immediate benefit is
sequential amortization at capacity one. Capacity two should be enabled only
for an explicitly selected parallel slice after measurement.

Runtime capacity allows CI and developer machines to choose different limits
and makes capacities one, two, and four benchmarkable without recompilation.

## Consumer eligibility

The first Canic pilot contains root-topology tests that:

- only query state, or mutate exclusively captured canisters;
- do not advance PocketIC time;
- do not create or delete canisters;
- do not assert exact cycle balances or newly allocated principals;
- pass the same root readiness validation after build and restore.

Blob-storage and billing tests are a later reset-coverage exercise because
they combine multiple canisters, time, and cycles. Fleet Registry tests remain
fresh while they mutate allocation heads, create/delete canisters, advance
time, or change draining and registry-global state.

IcyDB retains its standalone SQL fixture pool. Future cross-canister upgrade or
migration suites may adopt this pool only after declaring their own reset
requirements.

## Benchmark and correctness plan

Measure these phases separately:

- cold topology construction;
- warm snapshot restoration;
- non-snapshot reset and readiness waiting;
- invariant validation;
- test body;
- stale teardown and rebuild latency;
- peak RSS and PocketIC server-process count.

Compare:

1. current fresh serial setup;
2. one current cached serial baseline;
3. runtime pool capacity one;
4. runtime pool capacity two with selected parallel tests.

Start with capacities one and two. Capacity four is measured only if two shows
a useful throughput gain within memory limits.

Required stress coverage includes:

- 100 consecutive restores of one slot;
- concurrent leases with deterministic slot isolation;
- waiter ordering and no lost wakeups;
- test panic while holding a lease;
- recipe-hook panic;
- killed PocketIC server;
- snapshot restore, reset, readiness, and validation failures;
- original failure plus rebuild failure preservation;
- explicit lease invalidation;
- time advancement and cycle mutation;
- creation or deletion of an extra canister;
- built/restored invariant equivalence.

The generic implementation suite now covers every item above. Its destructive
transport test launches PocketIC with `reuse: false`, owns that child process,
and reaps it after killing it, so unrelated PocketIC tests retain their shared
server. The test is ignored by default and run explicitly in isolation because
PocketIC `start_server` currently waits indefinitely for a port file if its
child exits before binding. Normal fallible construction now avoids that path
through bounded `PocketIcStartupConfig`; this ignored destructive test still
uses the upstream function because it intentionally needs the returned child
handle to kill the dedicated server. Capacity-one queue timing and
capacity-two overlap are covered normally, while realistic throughput, peak
RSS, and server-process measurements remain part of the downstream Canic
pilot.

Run the destructive case by itself with:

```bash
cargo test -p ic-testkit --test pocket_ic_baseline_pool \
  killed_dedicated_server_rebuilds_on_a_fresh_server -- --ignored --exact
```

Because the pool owns one recipe structurally, ordinary acquisitions cannot
supply a mismatched recipe. Tests instead prove that the pool's recipe identity
is present in every receipt and that validation rejects a different identity
rather than rebuilding.

2. Done: add recipe identity, typed reset requirements/receipts, structured

3. Done: implement the baseline pool and prove capacity-one lifecycle behavior

4. Done: migrate the standalone pool scheduler and make its structured outcome

5. Done: publish a compile-checked external-consumer recipe demonstrating the

6. Pilot eligible Canic read-only root tests at capacity one.
7. Benchmark capacity two and measure peak memory/server count with a selected
   parallel Canic test slice.
8. Expand one reset domain at a time; do not begin with billing or Fleet
   Registry tests.

## Non-goals

- Automatically deriving a complete recipe identity.
- Claiming that named canister snapshots reset the complete PocketIC instance.
- Swallowing assertion or recipe panics as cache misses.
- Making tests parallel merely by configuring capacity above one.
- Embedding Canic topology, role, readiness, or billing behavior in
  `ic-testkit`.
- Replacing fresh instances for lifecycle-sensitive tests.
