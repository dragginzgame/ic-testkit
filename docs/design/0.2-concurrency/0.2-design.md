# 0.2 Concurrency-Neutral PocketIC Ownership and API Design

## Status

Accepted and implemented. Direct ownership, the re-export-based API, guard
removal, and overlapping-instance regression shipped in 0.2.0. Version 0.2.2
removes the remaining construction shims and thin time extension so the
current API follows the boundary described below. PocketIC server
acquisition and cache ownership are delegated upstream.

This document supersedes the earlier proposal for a `PicRuntimeLease`,
process-local exclusivity, and a host-wide advisory lock.

## Decision

`ic-testkit` is concurrency-neutral.

- `ic-testkit` re-exports `pocket_ic::PocketIc` and
  `pocket_ic::PocketIcBuilder`; it does not wrap either type.
- Each test should normally create and directly own a fresh `PocketIc`.
- `ic-testkit` does not impose process-wide or host-wide PocketIC
  serialization.
- Downstream test suites control resource parallelism through the Rust test
  runner or their CI configuration.
- Locks are permitted only around a genuinely shared resource and are scoped
  to that resource.

The 0.2 implementation removes `Pic`, `PicBuilder`, and `PicSerialGuard`
rather than replacing the guard with a hidden lease or retaining a forwarding
wrapper.

## Evidence

This decision follows the PocketIC concurrency model rather than treating host
serialization as an `ic-testkit` invariant:

- The PocketIC server supports many independent IC instances.
- The official PocketIC testing guide describes parallel execution as one
  `PocketIc` instance per test.
- The PocketIC Rust documentation says that sharing one instance among test
  cases is generally not recommended.
- `PocketIc::drop` cleans up its instance and stops and joins any progress
  thread it owns, so direct ownership also owns teardown.
- PocketIC exposes `submit_call`, `await_call`, `await_call_no_ticks`, and
  ingress-status APIs for concurrent ingress within one IC instance.
- The IC management-canister interface defines the Wasm chunk store as storage
  associated with a canister. Chunk-store exhaustion is therefore not a sound
  justification for serializing every PocketIC instance on a host.

References:

- [PocketIC 15 Rust documentation](https://docs.rs/pocket-ic/15.0.0/pocket_ic/)
- [`PocketIc` drop implementation](https://docs.rs/pocket-ic/15.0.0/src/pocket_ic/lib.rs.html#1712-1720)
- [ICP PocketIC testing guide](https://docs.internetcomputer.org/guides/testing/pocket-ic/)
- [`PocketIc::submit_call`](https://docs.rs/pocket-ic/15.0.0/pocket_ic/struct.PocketIc.html#method.submit_call)
- [`PocketIc::await_call`](https://docs.rs/pocket-ic/15.0.0/pocket_ic/struct.PocketIc.html#method.await_call)
- [`PocketIc::await_call_no_ticks`](https://docs.rs/pocket-ic/15.0.0/pocket_ic/struct.PocketIc.html#method.await_call_no_ticks)
- [IC management-canister chunk-store interface](https://docs.internetcomputer.org/references/ic-interface-spec/management-canister/#ic-upload_chunk)

## Goals

- Make independent PocketIC instances safe and unsurprising under parallel
  `libtest` execution.
- Make upstream ownership sufficient: if a caller owns a `PocketIc`, it owns
  the instance and no separate lifetime token is required.
- Keep `ic-testkit` focused on typed Candid calls, contextual diagnostics,
  reusable install/snapshot policy, and fixtures.
- Keep shared-baseline synchronization local to the baseline being shared.
- Leave CPU, memory, file-descriptor, and CI capacity policy to downstream
  suites.
- Preserve deterministic intra-instance concurrency testing through PocketIC
  ingress APIs rather than host-thread scheduling.

## Non-Goals

- Do not implement a global PocketIC semaphore.
- Do not serialize all `PocketIc` construction inside one process.
- Do not coordinate `PocketIc` construction, ownership, or lifetime across
  threads or processes through a PID file, lock directory, advisory lock,
  semaphore, or daemon.
- Do not mirror `PocketIc` or `PocketIcBuilder` through local forwarding APIs.
- Do not implement `Deref` or introduce a local simulator newtype solely to
  attach convenience methods.
- Do not choose a universal `--test-threads` value for downstream projects.
- Do not use host threads as a model of concurrent IC ingress.
- Do not make IcyDB- or Canic-specific CI policy part of the crate API.

## Ownership and Construction

The ordinary ownership shape is the upstream type itself:

```text
test or fixture
└── pocket_ic::PocketIc
```

Default construction uses `PocketIc::new()` directly. Custom topologies use the
re-exported `PocketIcBuilder` and call its upstream `build()` method. ic-testkit
does not catch or classify PocketIC startup panic text. Server discovery,
downloading, and caching remain PocketIC responsibilities:

```rust,ignore
pub use pocket_ic::{PocketIc, PocketIcBuilder};
```

There is no hidden owner, lease, or global coordination step. Dropping the
returned `PocketIc` invokes upstream teardown directly.

Standalone fixtures own their `PocketIc` directly:

```text
StandaloneCanisterFixture
├── PocketIc
└── canister_id
```

Consequently, `StandaloneCanisterFixture::into_parts()` safely returns
`(PocketIc, Principal)`: the returned upstream value continues to own its
instance, and no independent guard can be dropped too early.

Fixture installation consumes a caller-built instance:

```rust,ignore
StandaloneCanisterFixture::install(pocket_ic, install_spec);
StandaloneCanisterFixture::try_install(pocket_ic, install_spec)?;
```

This lets the caller choose topology, server URL, or an exact server binary
through upstream builder APIs without introducing an ic-testkit builder
wrapper.

### Harness Extension Boundary

Callers use inherent `PocketIc` methods for simulator operations. `ic-testkit`
adds extension traits only where it contributes typed encoding, contextual
diagnostics, or reusable policy. Initial focused traits are:

- `CandidCallExt` for typed Candid calls and contextual codec/call errors;
- `CanisterInstallExt` for generic install specifications, diagnostics, and
  install-code retry policy;
- `PocketIcSnapshotExt` for controller-aware snapshot sets;
- `PocketIcDiagnosticsExt` for reusable failure reporting.

Traits must not forward upstream operations merely for naming convenience.
Fixtures may expose forwarding methods when binding the fixture's canister id
is itself useful harness behavior.

Because `PocketIc` already has inherent byte-oriented `query_call` and
`update_call` methods, the typed extension methods use explicit names such as
`query_candid`, `update_candid`, `query_candid_as`, and `update_candid_as`.
They do not attempt to shadow upstream methods.

## Removed 0.1 Surfaces

0.2 removes the following surfaces and implementation:

- the `Pic` newtype and all pass-through methods;
- `PicBuilder`;
- `PicSerialGuard`
- `PicSerialGuardError`
- `acquire_pic_serial_guard`
- `try_acquire_pic_serial_guard`
- the `pic::process_lock` module
- `StandaloneCanisterFixtureError::SerialGuard`
- guard fields in `StandaloneCanisterFixture` and cached baselines
- PID/start-time owner records, `/proc` inspection, stale lock-directory
  reclamation, and global lock retry loops

The 0.1 requirement that a guard outlive `Pic` is deleted from API and README
documentation. There is no deprecated `Pic` alias or compatibility newtype:
callers remove the guard, use `PocketIc` directly, and import only the
extension traits they need.

Before:

```rust,no_run
use ic_testkit::pic::{Pic, acquire_pic_serial_guard, pic};

let _guard = acquire_pic_serial_guard();
let pic: Pic = pic();
```

After:

```rust,no_run
use ic_testkit::pic::{CandidCallExt, PocketIc};

let pocket_ic = PocketIc::new();
let value: u64 = pocket_ic.query_candid(canister_id, "get", ())?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

## Cached Baselines

`CachedPocketIcBaseline` is an explicit exception to the fresh-instance-per-test
default because its purpose is to reuse one expensive baseline.

Its existing caller-owned slot provides the correct synchronization boundary:

```text
Mutex<Option<CachedPocketIcBaseline<T>>>
└── CachedPocketIcBaseline
    ├── PocketIc
    ├── snapshots
    └── metadata
```

`CachedPocketIcBaselineGuard` holds only that slot's mutex guard. It prevents two
tests from mutating the same cached baseline concurrently, but it does not
block construction or use of unrelated `PocketIc` instances or baselines in
other slots.

The baseline API must document that sharing is explicit and local. Ordinary
tests should continue to prefer a fresh instance.

## Downstream Capacity Guidance

Parallelism is an operational property of a test suite, not a hidden runtime
policy in `ic-testkit`.

Ordinary unit tests remain parallel. Heavy PocketIC integration targets can
start conservatively, for example:

```bash
cargo test --test pocket_ic_e2e -- --test-threads=1
```

Canic and IcyDB are recommended to use that as the initial CI default for their
heavy E2E target. Their rollout changes are tracked in those repositories and
are not an acceptance requirement for the `ic-testkit` 0.2 release. A suite
may deliberately raise the value to `2` or higher after observing stable CPU,
memory, and file-descriptor usage under load. Such a change is CI capacity
tuning, not an `ic-testkit` correctness change.

`ic-testkit` may document this runner control, but it must not read an
environment variable or silently enforce a parallelism limit itself.

## Concurrency Within One IC Instance

Tests of concurrent ingress should use PocketIC's deterministic ingress
surface:

1. Submit every relevant ingress message with `PocketIc::submit_call` before
   awaiting any result.
2. When exact round boundaries matter, advance execution explicitly with
   `PocketIc::tick`, inspect ingress status, and collect results with
   `PocketIc::await_call_no_ticks`.
3. Use ordinary `PocketIc::await_call` when its progress behavior does not
   affect the scenario being tested.

These are upstream operations and receive no `ic-testkit` wrappers.

Host threads are not a substitute for IC message concurrency. They introduce
host scheduling into a test whose relevant concurrency belongs inside the IC
instance.

## Resource-Scoped Locking

Removing global PocketIC serialization does not prohibit all locking. A lock
is appropriate when its scope matches one shared resource:

- Benchmark output: callers coordinate writers only when they target the same
  output path; unique run directories need no global lock. Path-derivation
  helpers do not reserve a directory or impose hidden synchronization.
- Cached baseline: use the mutex for that specific baseline slot.

These locks must not be stored in a simulator wrapper or acquired for
unrelated instances.

The general host-resource invariant is:

> Every mutable host resource used by `ic-testkit` must either be unique to one
> `PocketIc` or test invocation, or be an explicitly shared resource protected by
> synchronization keyed only to that resource. No resource guard may be stored
> with a `PocketIc` or retained for the lifetime of a PocketIC instance.

This applies to future temporary directories, output paths, and shared statics
as well as the currently known resources.

The process environment is a separate hard boundary. `ic-testkit` treats it
as caller-owned, read-only configuration during test execution. The crate does
not set, remove, or otherwise mutate environment variables to coordinate tests
or manage `PocketIc` ownership. An internal lock cannot make process-wide
environment mutation safe with unrelated caller code.

### Upstream-Owned Server Acquisition

`ic-testkit` does not download, publish, validate, or lock a PocketIC server
binary. Callers configure the re-exported `PocketIcBuilder`; PocketIC owns
`POCKET_IC_BIN`, its default download behavior, and its cache. Consequently,
no binary-cache guard can become coupled to `PocketIc` construction or
lifetime inside `ic-testkit`.

PocketIC lifecycle and transport failures that still panic remain a temporary
upstream compatibility boundary. The internal panic-catching and dead-instance
message classification must be deleted once upstream provides fallible APIs
with structured transport variants for the operations used here. They are not
permission to add a parallel PocketIC lifecycle abstraction.

## Acceptance Tests

The primary concurrency test is intentionally the opposite of global
serialization and uses bounded coordinator channels:

1. Start two worker threads and release both from the coordinator.
2. Each worker constructs its own `PocketIc`, retains it, and sends `Ready`.
3. Require both `Ready` messages within a test-only deadline. The deadline
   detects an ownership regression within a bounded period.
4. Only after both instances are confirmed alive does the coordinator allow
   the workers to install and operate their canisters.
5. Give the two instances different state and prove isolation.
6. Drop instance A while instance B remains alive.
7. Make another successful call against B, then allow B to drop.

Host threads are correct in this acceptance test because it proves concurrent
host ownership of independent instances. They remain inappropriate for
modelling concurrent ingress inside one instance. The test-only channel
deadline is not a runtime ownership or acquisition timeout.

On that deadline, the coordinator closes all release and cancellation
channels. Any ready worker treats closure as cancellation and drops its
retained `PocketIc`. That teardown allows a second worker blocked by an accidentally
reintroduced ownership lock to progress, observe cancellation, and exit. The
coordinator then joins both workers. Because a channel deadline cannot forcibly
cancel a thread stuck for some unrelated reason inside `PocketIc` construction, the
live test also has an outer CI process or job timeout as its final deadlock
boundary.

Additional acceptance checks:

- `StandaloneCanisterFixture::into_parts()` returns a usable live `PocketIc`.
- Holding one `CachedPocketIcBaselineGuard` does not prevent an unrelated
  thread from constructing and using a fresh `PocketIc`.
- Two different cached-baseline slots do not share a mutex or global lease.
- No ic-testkit-managed PocketIC downloader, binary cache, publication lock,
  or cache recovery path remains.
- No process-wide or host-wide `PocketIc` ownership lock, lease, acquisition
  timeout, owner record, or retry loop remains in the public API or
  implementation.
- README examples show one fresh `PocketIc` per ordinary test and runner-level
  capacity tuning for heavy E2E targets.

The overlapping-instance acceptance test must run in the live PocketIC CI lane
for every supported PocketIC client/server pair and whenever either the
PocketIC dependency or server version changes. It runs on every host platform
that `ic-testkit` claims to support, currently at least Linux and macOS. Unit
tests for ordinary crate logic remain parallel.

## Relationship to Other 0.2 Work

The following related 0.2 work is also implemented:

- structured `CanisterReject` call errors;
- ordered, duplicate-checked, fallible snapshot sets with partial cleanup;
- one explicit install retry policy;
- an internal aggregate scope that cannot collide with an authored `ALL`
  suite;
- removal of the duplicate ic-testkit downloader and cache in favor of
  upstream PocketIC ownership.

Measuring whether a separate canister marker crate is worth its workspace and
publication cost is deferred until size data justifies that extra package.

None of those workstreams should reintroduce global `PocketIc` serialization
or a forwarding simulator wrapper.

## Implementation Sequence

1. Before cleanup, add a live upstream proof using raw
   `pocket_ic::PocketIc` instances and the bounded coordinator protocol.
2. Re-export `PocketIc` and `PocketIcBuilder`, use their upstream construction
   APIs directly, and remove the `Pic` newtype and its pass-through methods.
3. Move value-adding behavior to focused extension traits, using explicit
   Candid method names that do not collide with inherent upstream methods.
4. Remove `process_lock` and all guard types, exports, fields, and errors.
5. Supplement the upstream proof with regressions through value-adding public
   fixture and cached-baseline paths.
6. Simplify standalone and cached-baseline construction around direct
   `PocketIc` ownership.
7. Update README examples and delete the chunk-store serialization rationale.
8. Remove the duplicate ic-testkit server downloader, cache, runtime policy,
   and related direct dependencies; delegate acquisition upstream.
9. Run the full live PocketIC release gate with the overlapping-instance test
   on Linux and macOS.

At no point should implementation introduce a replacement `PicRuntimeLease`
or any process-wide or host-wide control governing `PocketIc` construction,
ownership, or use.
