# Concurrency-Neutral PocketIC Ownership

## Status

Historical decision record, accepted and implemented. The README and generated
rustdoc describe the current API.

## Decision

ic-testkit is concurrency-neutral:

- each test normally constructs and owns a fresh `PocketIc`;
- `PocketIc` and `PocketIcBuilder` are direct upstream re-exports;
- no ic-testkit type governs process-wide or host-wide instance ownership;
- downstream test runners and CI schedulers control resource parallelism;
- synchronization is permitted only for a genuinely shared resource and is
  scoped to that resource.

PocketIC 15 supports independent concurrent instances and discourages sharing
one instance between unrelated test cases. Direct ownership also makes
`PocketIc::drop` the instance-cleanup boundary.

## Object model

```text
test invocation
  -> owns PocketIc
      -> owns one upstream PocketIC instance

StandaloneCanisterFixture
  -> owns PocketIc
  -> stores one installed canister id

CachedPocketIcBaseline<T>
  -> owns PocketIc
  -> stores one ordered snapshot set
  -> stores caller metadata
```

`StandaloneCanisterFixture::into_parts()` safely returns the owned instance and
canister id. No external lease needs to outlive either value.

## API boundary

Native simulator operations remain upstream inherent methods. ic-testkit adds
focused extension traits only where it contributes typed encoding, contextual
diagnostics, deterministic policy, or reusable harness state:

- `CandidCallExt`;
- `CanisterInstallExt`;
- `PocketIcSnapshotExt`;
- `PocketIcDiagnosticsExt`;
- `PocketIcBuilderExt`;
- `PocketIcTimeExt`.

The trait-only `pic::prelude` groups those imports. It does not re-export data
types or mirror the rest of PocketIC.

## Cached-baseline exception

A cached baseline intentionally reuses one expensive instance across tests.
The caller supplies a specific `Mutex<Option<CachedPocketIcBaseline<T>>>` slot,
and the returned guard retains that slot lock while the baseline is in use.

This serializes only users of the same slot. Different baseline slots and fresh
PocketIC instances remain independent.

On a cache hit, the caller's restore closure runs against the existing
baseline. A recognized dead-instance transport panic evicts and rebuilds that
baseline. Unrelated panics resume unwinding.

## Shared host resources

Every mutable host resource must either be unique to one invocation or guarded
by synchronization keyed only to that resource. Examples include one report
output path or one cached-baseline slot.

No resource guard is stored with a `PocketIc` or retained merely because an
instance is alive. The process environment is caller-owned, read-only
configuration during test execution.

PocketIC owns its binary discovery, download, validation, and cache behavior.
ic-testkit does not couple cache acquisition to instance lifetime.

## Concurrency inside one instance

Host threads are suitable for proving that independent instances can overlap.
They are not the preferred model for concurrent ingress within one IC.

For deterministic same-instance ingress tests:

1. submit every relevant message with `submit_call`;
2. advance execution explicitly when exact round boundaries matter;
3. inspect status and use `await_call_no_ticks` for controlled progress;
4. use ordinary `await_call` when its progress behavior is part of the test.

These are upstream PocketIC operations; ic-testkit does not mirror them.

## Capacity policy

Resource-heavy suites may begin with:

```bash
cargo test --test pocket_ic_e2e -- --test-threads=1
```

Raising the value is downstream CI capacity tuning, not a correctness change in
ic-testkit. Ordinary unit tests should remain parallel.

## Validation invariant

The live concurrency test retains two independently created instances at the
same time, proves isolated state, drops one while the other remains alive, and
then successfully uses the survivor. This test runs whenever the supported
PocketIC client/server line changes and on each claimed host platform.

The channel deadline detects an ownership regression; the outer CI job timeout
remains the final deadlock boundary.
